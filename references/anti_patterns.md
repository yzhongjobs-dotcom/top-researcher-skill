# 通用反例

从一个机器人接触控制项目的实际偏差中抽象出来，去掉了具体 idea。每条写：表现 → 后果 → 正确做法。新一轮逆向分析中，凡能在顶刊样本里找到对照做法的，补上链接。

| 反例 | 典型表现 | 后果 | 正确做法 |
|---|---|---|---|
| **过度防守** | 看到强 prior 就避让；要求某个部件必须独有、模块必须原创，或先证明所有已有方法失败才肯设计 | 有分量的问题越缩越小，调研变成阻止设计方法的关卡 | 按任务能力理解已有工作，追问剩余的重要局限并改进；成熟方法可直接借鉴或小改造，不由部件重合判整套贡献 |
| **按算法名字判重合** | 外域已有同名机制，就当成否定 idea 的理由 | 可迁移的成熟机制被浪费 | 区分是否已在相同任务、相同条件下实现所需能力；外域机制是设计资源，核查适配条件 |
| **渐进偏题** | 从原问题逐步滑向“某种更新有多大价值”“整段资源规划”等更容易做的问题 | 原问题被暗中替换，读者不知道研究到底解决什么 | 每次改动说明是否仍回答原任务；实质换题交代依据与影响，由用户决定 |
| **实现与方案名称不符** | 原构想是“估计 + 离线学习快速生成阻抗”，实际实现成“短历史直接强化学习”，仍用原方案名称下结论 | 实验没有验证原构想，后续判断累积错误 | 写清原构想、拟改造与实际实现各自的输入、训练、输出与执行；结论只针对实际被测对象 |
| **简单拼接代替设计** | 追加策略库、观察器、后验规划等模块，说不清它们怎样共同解决问题 | 代码和实验很多，仍没有可信方法 | 从所需能力解释各机制的分工与配合；不用模块数量或新名称作贡献 |
| **局部结果推及整体** | 一个简化载体上固定/简单策略接近，就否定整个方向；或反过来用“只是局部”无限保护原方案 | 对方向下了超出证据的结论 | 说明省略了哪些关键结构，判断结果限制的是实现、机制还是问题 |
| **实验目标失真** | 给方法理想真值标签；用信息代理指标代替任务收益；考虑不断加难度让算法赢 | 胜负与真实任务改善脱节 | 任务损失来自实际动力学和需求；条件有依据；区分参考/前馈收益与增益收益 |
| **控制器偏好代价当成绩** | 用含增益偏好、变化率惩罚的完整代价比较，自己的方法“更低” | 独立物理指标上其实输给对照 | 共同评分只用任务物理指标，偏好项单列 |
| **无意削弱对照** | 给对照方法强加原文没有的参数约束；适配时值域写错导致大量求解失败；消融替换错了参数 | 夸大自己的优势，结论需要撤回 | 核对原文方程与自由度，检查运行输入范围内的适配有效性，公平给予调参预算 |
| **理论对象与数值对象混淆** | 把数值方程的根当成优质策略，把条件性的界当成实际保证，把软件计时当成实时认证 | 最优性、稳定性、实时性被夸大 | 分清理论对象、数值近似、实际闭环和部署成本，结论对准所检查的对象 |
| **忽略完整成本** | 只计预测不计校验与重锚；立即执行性能当部署性能 | 加速或控制收益被高估 | 记录准备、更新、发布和持续反馈的全链成本；普通快速求解器公平竞争 |
| **把更准的估计当贡献** | 历史信息使预测不同，但选出的增益只改善很少 | 预测能力与任务能力混为一谈 | 直接检查信息怎样改变动作和力/运动表现；普通观察器足够时就直接采用 |
| **稻草人式立题与概括** | 写“已有几类方法都忽略某因素/各自必然失效”，被原文推翻 | 审稿人一眼看出，可信度受损 | 如实写出强 prior 做到了什么，再讲具体区别 |
| **把自己的机制预设为必要前提** | 写“必须先分离两种来源才能控制”，但已有方法不分离也能处理 | 问题建立在错误前提上 | 把机制写成待验证的设计选择，用消融说明它的额外收益 |
| **记录替代推进** | 多轮“最新方案”、巨大清单和过时待办留在入口 | 新 agent 分不清已证事实、猜想和已撤回指令 | 入口只保留有效定义与证据，历史交给版本管理 |
| **汇报抽象** | 只报“补了 24 组”“下一步计划”，不说比较对象、理由和数字 | 用户无法判断进展 | 直接给数字、对象、原因和未完成内容 |
